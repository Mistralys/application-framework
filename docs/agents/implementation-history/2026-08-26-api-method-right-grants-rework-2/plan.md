## Summary

Replace `SetMailingStateAPI` — the single API method that multiplexes three distinct authorization requirements behind one method name — with three dedicated methods (`FinalizeMailingAPI`, `RevertMailingToDraftAPI`, `DeactivateMailingAPI`), each declaring its own right. Delete `SetMailingStateAPI` entirely. Also fix the `VariationAPITraitStub` missing `getRequiredRight()` method and extract a `canEditMethods()` helper in `APIKeyMethodsAction`.

## Architectural Context

**One-right-per-method model.** The framework's `APIKeyMethodInterface::getRequiredRight()` returns a single right string. The method index caches this value at build time. `APIKeyRights::satisfies()` reads the declared right from the index and checks a direct match or one-level `hasGrant()` expansion against the key's grants. The model does not support context-dependent rights (different rights for different parameter values).

**Grant hierarchy.** `RIGHT_FINALIZE_MAILS` (`PublishMails`) grants `RIGHT_EDIT_MAILS`, `RIGHT_CREATE_MAILS`, and `RIGHT_DELETE_MAILS`. The reverse does not hold — `RIGHT_EDIT_MAILS` does not grant `RIGHT_FINALIZE_MAILS`. However, this grant hierarchy does not translate into cross-method authorization: `BaseAPIMethod::authorize()` (`application-framework/src/classes/Application/API/BaseMethods/BaseAPIMethod.php`, L177-199) is the sole call site of `APIKeyRights::satisfies()`, and it always invokes it as `satisfies($this->getMethodName(), $this->getRequiredRight())` — a method's own name paired with its own declared right. `authorize()` also gates on `$key->getMethods()->hasMethod($this->getMethodName())` *before* `satisfies()` runs. As a result, the one-level `hasGrant()` expansion branch inside `satisfies()` is unreachable at this call site: a key must have each of `FinalizeMailingAPI`, `RevertMailingToDraftAPI`, and `DeactivateMailingAPI` explicitly granted as methods regardless of the right hierarchy between them. This is more conservative than a naive reading of the grant hierarchy would suggest, and is the correct authorization semantic.

**Current problem.** `SetMailingStateAPI` declares `RIGHT_EDIT_MAILS` as its required right but internally checks `RIGHT_FINALIZE_MAILS` on the pseudo-user for finalization transitions. Since `createTestAPIKeyForMethod()` no longer configures pseudo-user rights, all finalization calls fail with a 403 in tests, and the production authorization path is broken: the pseudo-user created from an API key has no rights assigned.

**Shared traits.** `MailAPITrait` provides `buildMailStateResponse()`, `buildMailDeepLinks()`, and mail parameter management. `DryRunAPITrait` provides dry-run parameter handling. `MailValidationAPITrait` provides `buildMailValidationResponse()`. These traits are already used by `SetMailingStateAPI` and will be reused by the new sub-methods.

**Autodiscovery.** `APIMethodCollection` scans `assets/classes/Maileditor/Mails/API/Methods/` recursively. New classes placed there are auto-registered — no manual registration needed.

**Nexus-plugins consumer.** The `api-methods.json` data file is auto-generated by `composer generate-api-methods-json` and consumed by the MCP server's `hcp_describe_api_method` tool. No TypeScript code references `SetMailingState` by name. After regenerating the JSON and running `npm run build`, new method names are automatically reflected.

## Approach / Architecture

Split `SetMailingStateAPI` into three dedicated API method classes and delete the original:

1. **`FinalizeMailingAPI`** — `targetState=finalized`. Declared right: `RIGHT_FINALIZE_MAILS`. Encapsulates validation, state change, and optional `rygnarokFinalize()` generation. Eliminates the Tier-2 pseudo-user rights check entirely — the framework's standard `authorize()` enforces the right via `satisfies()`.

2. **`RevertMailingToDraftAPI`** — `targetState=draft` (from finalized or inactive). Declared right: `RIGHT_EDIT_MAILS`. Simple state transition, no validation needed.

3. **`DeactivateMailingAPI`** — `targetState=inactive` (from draft or finalized). Declared right: `RIGHT_EDIT_MAILS`. Simple state transition, no validation needed.

Each method:
- Is a standalone `BaseAPIMethod` implementing the same interfaces as the current method (minus the validation response interfaces for the two non-finalization methods).
- Reuses existing shared traits (`MailAPITrait`, `DryRunAPITrait`, `APIKeyMethodTrait`, etc.).
- Has its own `compileRequestVars()` for programmatic invocation.
- Builds the same response shape (mailID, label, state, stateLabel, capability flags, deepLinks, dryRun).
- Handles its own no-op detection (current state equals target state).
- Validates that the transition is permitted by the state graph, returning error `185905` for invalid transitions.

No new base class or trait is introduced. The shared response building already exists in `MailAPITrait`.

## Rationale

- **Authorization by design.** Each method declares exactly one right, fitting the one-right-per-method model without exceptions. No Tier-2 pseudo-user checks, no dynamic `getRequiredRight()`, no framework modifications.
- **Clean deletion.** The only external consumer of `SetMailingState` is the auto-generated `api-methods.json` data file, which rebuilds automatically. No backward compatibility wrapper needed.
- **Each method requires its own explicit grant.** Because `authorize()` gates on `hasMethod($this->getMethodName())` before calling `satisfies()`, and `satisfies()` is always called with a method's own name/right pair, a key must have `FinalizeMailingAPI`, `RevertMailingToDraftAPI`, and `DeactivateMailingAPI` each explicitly granted — the `PublishMails → EditMails` right hierarchy does not let a key skip granting the other two methods. This is the actual (more conservative) authorization semantic; it should not be described as implicit cross-method grant expansion.
- **No framework changes.** The entire solution is contained in the HCP Editor's API methods layer.

## Considered Alternatives

| Decision | Chosen Shape | Alternatives Considered | Trade-Off Summary |
|----------|--------------|-------------------------|-------------------|
| Split approach | Three separate method classes, delete original | (a) Keep `SetMailingStateAPI` as a backward-compatible router that delegates to sub-methods; (b) Make `getRequiredRight()` dynamic based on request params | (a) Adds complexity for zero consumers — the MCP data file regenerates automatically; (b) doesn't work because `satisfies()` reads the index, not the runtime value, and storing `PublishMails` in the index would over-restrict non-finalization calls. |
| Number of methods | Three dedicated (finalize, draft, inactive) | (a) Two methods (finalize + one for all simple transitions with a `targetState` param) | Three methods give clean one-right-per-method alignment. Two methods would still require one method to handle both draft and inactive, which works but obscures the API surface. Three is cleaner for autodiscovery and the method index. |
| Shared code strategy | Reuse existing `MailAPITrait` methods | (a) New shared base class; (b) new shared trait for state response building | The response helpers already exist in `MailAPITrait`. A new abstraction layer for three small methods is over-engineering — each method is ~100 lines. |

## Pattern Alignment

- **Follows** the one-right-per-method model established by `APIKeyMethodInterface::getRequiredRight()` — `application-framework/src/classes/Application/API/Clients/API/APIKeyMethodInterface.php`.
- **Follows** the `{Verb}{Subject}API` class naming pattern in `hcp-editor/assets/classes/Maileditor/Mails/API/Methods/` — e.g. `DeleteMailingAPI`, `UpdateMailingAPI`.
- **Follows** the `{VerbSubject}` method name pattern — e.g. `DeleteMailing`, `UpdateMailing`.
- **Follows** the `compileRequestVars()` static helper pattern — e.g. `DeleteMailingAPI::compileRequestVars()`.
- **Follows** the `MailAuthoringAPIGroup` group assignment for write methods.
- **Follows** `array()` syntax, `declare(strict_types=1)` conventions.
- **Departs from** the previous single-method-for-all-transitions pattern. Justification: the previous pattern is incompatible with the one-right-per-method authorization model. The new pattern matches `DeleteMailingAPI` (which was already split out from `SetMailingState`'s conceptual scope).

## Assumptions

- The state graph permits `finalized → draft`, `inactive → draft`, `draft → inactive`, `finalized → inactive`, `draft → finalized` and rejects `inactive → finalized`. These transitions are verified by the existing `hasDependency()` method on the state objects.
- The state graph itself also permits `deleted → draft` (`STATUS_DELETED`'s dependency list is `array(STATUS_DRAFT)` only). `RevertMailingToDraftAPI` explicitly rejects this transition via an application-level guard, independent of what the state graph alone would allow.
- No external systems (CI, deployment scripts, other repositories) reference `SetMailingState` by name beyond what's in this workspace.
- The error codes `185905` (invalid transition), `185906` (validation failure), `185907` (generation failure) are reused by the new methods since they represent the same error conditions.

- The `MailValidationAPIResponseInterface` and `MailValidationAPITrait` are only needed by `FinalizeMailingAPI` — the other two methods have no validation step.

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| **Error code reuse confusion.** Using the same error codes (`185905`, `185906`, `185907`) across multiple methods could confuse API consumers who filter by code. | These codes represent the same semantic errors (invalid transition, validation failure, generation failure). Reuse is intentional and consistent — consumers already handle them. |
| **State graph validation divergence.** Three methods each validating their own transitions could drift from the canonical state machine. | All three methods use the same `$currentStateObj->hasDependency($targetStateObj)` call. The state graph is the single source of truth — methods don't hardcode valid transitions. |
| **Grants do not expand across methods — must be documented accurately.** Despite `PublishMails` granting `EditMails` in the right hierarchy, a key granted only `FinalizeMailingAPI` does *not* automatically gain `RevertMailingToDraftAPI` or `DeactivateMailingAPI`: `BaseAPIMethod::authorize()` gates on `hasMethod($this->getMethodName())` before calling `satisfies()` with a method's own name/right pair, so the `hasGrant()` cross-method expansion branch is unreachable in practice. | Each of the three methods must be explicitly granted on an API key regardless of the right hierarchy between them. Admin-facing guidance and support documentation must not claim that granting `FinalizeMailingAPI` implicitly enables the other two. |
